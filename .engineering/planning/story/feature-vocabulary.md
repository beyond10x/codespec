# Story: The cir/1 feature vocabulary

## Outcome

`codespec features` prints `codespec-features/1`: every feature id of `docs/conformance.md` § 2,
generated from the model, written to `schemas/cir-1.features.json` and drift-checked.

## Acceptance

- `codespec features` output equals the checked-in `schemas/cir-1.features.json`; a test fails when
  they differ, as the schema's drift test does.
- Statement, expression, type and declaration ids come from the model itself: the `"const"` values
  of the `k` tag in the generated JSON schema (`codespec_model::schema_json`), not a hand list. A
  test checks the counts: 16 statement kinds, 17 expression kinds, 12 types, 4 declarations, 7
  facts; adding a variant to `crates/model/src/lib.rs` without regenerating fails it.
- Operator, intrinsic and semantic ids are a constant list beside the generator, each with a
  one-line description; the semantic ids include at least `sem.int.wrap`, `sem.rem.sign`,
  `sem.continue.post`, `sem.multi_assign.order`, `sem.map.order`.
- The ids are sorted and unique; `codespec features` run twice gives the same bytes.

## Scope

- `crates/model/src/features.rs` (new), the `mod` line in `crates/model/src/lib.rs`.
- `crates/cli/src/lib.rs`, `crates/cli/src/main.rs`: the `features` subcommand.
- `schemas/cir-1.features.json` (new).
- `website/docs/reference/cli.md`: regenerated by `task docs-generate` for the new subcommand.
- `Taskfile.yml` `schema` task: the coordinator's (the unit writes a patch).
